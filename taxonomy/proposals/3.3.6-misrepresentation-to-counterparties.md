# Proposal: 3.3.6 Agent misrepresentation to external counterparties

**Status:** proposed, 2026-08-11
**Parent:** 3.3 Interfaces and boundaries
**Proposed code:** 3.3.6

## Rationale

An agent transacting on an organization's behalf can deceive the party on the
other side — misstating its authority, its constraints, or facts material to
a deal. This is now an observed behaviour rather than a hypothetical: the
Vending-Bench Arena results of July 2026 include supplier deception alongside
price collusion and truce-breaking.

The taxonomy has no node for it, and the three adjacent candidates each
describe something else:

- **3.3.3 Agent interaction with external systems and counterparties** — the
  interface where this happens, not the behaviour. Tagging it there says an
  interaction occurred, which is true of every external transaction.
- **10.2 Attacks by agents** — infrastructure: sandbox escape, privilege
  escalation, lateral movement. Lying to a supplier compromises no system.
- **5.2.2 Agent collusion and cartel formation** — agents coordinating with
  *each other*. Deception of a counterparty is the opposite arrangement.

The organizational stakes are also distinct from the technical ones. Where
agents misrepresent on the organization's behalf, exposure is contractual and
reputational, and the questions that follow — who is liable, what disclosure
is owed — run into 12.2 and 12.5 rather than into the security sections.

## Why not an alias

An alias makes an existing topic findable under another name. There is no
existing topic here whose meaning includes this behaviour, so an alias would
misdirect rather than help.

## Example resources

- Vending-Bench Arena (Andon Labs) — supplier deception, observed
- Dissociative Identity: Language Model Agents Lack Grounding for Reputation
  Mechanisms (arXiv:2605.30169) — why an agent's representations of itself
  are hard to bind to anything, which is the mechanism underneath

## Open question for leadership

Whether this belongs in 3.3 (a property of the external boundary) or in a
failure code under 11.x (a thing that goes wrong). A case exists for both,
and the coding scheme in section 11 would let an incident carry it alongside
the failure modes it triggers. Section 3.3 is proposed because the behaviour
is a design consideration before it is an incident — you want it in view when
deciding what an agent may transact, not only when reviewing what went wrong.
